# 計画: 明示保存 + Undo への移行

現行の「編集＝元 `.dbml` を即上書き」「ファイル監視で外部変更を再描画」というモデルを、
**普通のドキュメントエディタと同じ「編集はメモリに溜め、保存で書き込む」モデル**へ作り替える計画。
あわせて **テーブル定義編集の無限 Undo** を導入する。

背景: 通常 `.dbml` は git リポジトリ内にあり、他者との衝突は `git pull` で解決される。
アプリがファイル監視で勝手に再読込・即上書きするより、**開いた時点のスナップショットを編集し、
明示的に保存する**方が編集体験・事故防止の両面で望ましい（2026-07-14 ユーザー決定）。

関連ドキュメント: [全体設計.md](全体設計.md) / [実装計画.md](実装計画.md)（フェーズ4/5）/ [UI設計.md](UI設計.md) / [設計-視点移動.md](設計-視点移動.md)

## 決定事項（2026-07-14）

- **即上書きをやめる**。編集はメモリ上に溜め、**「保存」ボタン + Cmd/Ctrl+S** で明示的にファイルへ書き込む。
- **ファイル監視（watch）を廃止**する。外部変更検知・保存衝突ダイアログも撤去（衝突は git 側で解決する前提）。
- **テーブル定義編集の無限 Undo（Cmd/Ctrl+Z）** を入れる。対象は「テーブル定義を触った操作」＝ カラム追加・編集・削除。
  - **テーブル位置・幅などの見た目状態（サイドカー）は Undo 対象外**。
- **編集状態の保持方式は「編集済みテキストのスナップショット履歴」**（方式1）。
  - DBML は最大でも数十KB。スナップショットを多数ためてもメモリは数MB規模で問題にならない。
  - 各編集は既存の最小編集関数（`insertColumnLine` / `replaceColumnLine` / `deleteColumnLine`）で
    「現在のテキスト → 新テキスト」を生成し、履歴に push する。**最小編集による書式保持がそのまま生きる**。
- 未保存の変更があるまま別ファイルを開く/閉じる操作では**確認ダイアログを出す**。
- 監視廃止に伴い、VSCode 等での外部編集は**「再読み込み」ボタンでユーザーが明示的に取り込む**
  （自動では反映しない）。VSCode との疎結合連携自体は維持し、リアルタイム自動再描画から手動リロードへ変える。
  未保存編集がある状態でのリロードは破棄確認を出す。

## 現状との差分

| 項目 | 現状 | 変更後 |
| --- | --- | --- |
| 編集の反映 | 確定ごとに `writeTextFile` で即上書き | メモリ上のテキストを更新するだけ。保存操作で初めて write |
| 真実の source | ディスク上のファイル（毎回 `readTextFile`） | メモリ上の現在テキスト（`currentText`） |
| ファイル監視 | `watch` で外部変更を再描画 | 廃止 |
| 外部変更/保存衝突 | 保存衝突ダイアログ | 廃止 |
| Undo | なし | テキストスナップショット履歴で無限 Undo/Redo |
| 未保存状態 | 概念なし（常に保存済み） | dirty フラグを持ち、タイトル/保存ボタンに反映 |

## 設計

### 編集状態の持ち方

現在の内部モデル `model`（`DbmlModel`）は**現在テキストのパース結果**という位置づけを維持する。
新たに「現在の DBML 全文テキスト」を単一の真実として保持する。

```
currentText: string           // いま画面が表しているDBML全文（未保存編集を含む）
savedText:   string           // 最後にディスクへ書いた（or 開いた）内容。dirty判定の基準
model:       DbmlModel        // currentText をパースした結果（描画・検索・フォーカスの元）
isDirty = currentText !== savedText
```

各編集操作は次の純関数フローで `currentText` を更新する（既存の最小編集をそのまま流用）:

```
newText = insert/replace/deleteColumnLine(currentText, table, ...)  // ← readTextFile をやめ currentText を渡す
  → parseDbml(newText) で検証（不正なら適用せずトースト）
  → 履歴へ push（Undo用）
  → currentText = newText, model = 再パース結果
  （write はしない）
```

> 重要: 最小編集関数の入力を「ディスクの最新内容」から「メモリの currentText」に替えるだけで、
> 関数自体（書式保持ロジック）は無改修で使える。token（位置情報）は毎回の再パースで更新されるため、
> 積み上げ編集でも整合する。

### 保存

- **保存ボタン**（[TopBar.tsx](../src/view/TopBar.tsx)）＋ **Cmd/Ctrl+S**。
- 動作: `writeTextFile(filePath, currentText)` → `savedText = currentText`（isDirty=false）。
- 保存成功トースト。失敗はエラートースト（現行踏襲）。
- **保存時に Undo 履歴はクリアしない**（保存後も直前の編集を Undo できてよい。保存済み↔未保存は dirty で表現）。

### Undo / Redo

- **テキストスナップショットのスタック**で実装する（`past: string[]` / `future: string[]` / `present: string`）。
  - 編集適用時: `past.push(present); present = newText; future = []`。
  - Undo: `future.unshift(present); present = past.pop()`。
  - Redo: `past.push(present); present = future.shift()`。
- Undo/Redo のたびに `model` を再パースし直す（`present` は常にパース可能なテキストのはず＝適用時に検証済み）。
- **無限**（上限を設けない）。DBML の規模的にメモリ問題は起きない。
- ショートカット: Cmd/Ctrl+Z（Undo）、Cmd/Ctrl+Shift+Z（Redo）。テキスト入力中（ColumnEditRow 等）の
  IME/フィールド内 Undo と衝突しないよう、フォーカスが入力要素にある間はグローバル Undo を発火させない。
- **見た目状態（位置・幅）は履歴に含めない**。これらはサイドカーへ従来どおり即保存で構わない。

### ファイル監視の廃止と手動リロード

- [useDbmlFile.ts](../src/parser/useDbmlFile.ts) の `watch` / `startWatching` / `unwatchRef` / 自己保存反響検知
  （`lastWrittenContentRef`）/ 編集セッション連動（`setEditSessionOpen` / `onExternalChangeDuringEdit`）を撤去。
- [App.tsx](../src/App.tsx) の保存衝突ダイアログ（`conflictDialogOpen` / `handleDiscardAndReload` / `handleKeepMyEdit`）を撤去。
- `modelUpdate` の `reload` 種別は残す（**手動リロードで使う**）。ただし発生源は「watch の自動再読込」から
  「ユーザーがリロードボタンを押した」に変わる。視点移動での扱い（視点維持）は従来どおり。
- **手動リロードボタン**（[TopBar.tsx](../src/view/TopBar.tsx)）を追加し、`reloadFromDisk` 相当でディスクの最新内容を
  読み直して `currentText`/`savedText`/`model` を差し替える。未保存編集があれば破棄確認ダイアログを出す。
  取り込み後は Undo 履歴をクリアする（別内容に差し替わったため、それ以前の編集は Undo 不能でよい）。

### 未保存破棄のガード

- 未保存（isDirty）で以下を行おうとしたら確認ダイアログ（「保存していない変更があります。破棄しますか?」）:
  - 別ファイルを開く（ダイアログ / 履歴）
  - アプリを閉じる（Tauri のウィンドウクローズ要求をフックして確認）
- 選択肢: 「保存して続行」/「破棄して続行」/「キャンセル」。

## 未決事項・論点

- **保存前パースエラーの扱い**: 各編集は適用時に検証するので `currentText` は常にパース可能な想定。
  だが将来テキスト直接編集を許すなら、保存時にも `validateBeforeSave` 相当を通すか要検討。
- **Redo をどこまで残すか**: 保存後に Undo→別編集をした場合、future は破棄（一般的な挙動）でよいか。
- **ウィンドウクローズのフック**: Tauri 側（`onCloseRequested`）の実装が必要。Rust 側 or JS 側どちらで持つか。
- **dirty の粒度**: 「見た目だけ変更（位置・幅）」は dirty に含めない（サイドカーは別管理）。この線引きを明記済みだが、
  UI 上「未保存」の意味がユーザーに伝わるか（本体の未保存のみを指す）を確認したい。

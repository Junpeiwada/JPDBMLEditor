# 設計: 視点移動（カメラのパン/ズーム）の発動条件

ER 図キャンバスの**視点（カメラ）をいつ自動で動かすか**を定めた設計書。フォーカス/検索を「薄表示 + 視点ズーム」方式に変更した際（[UI設計.md](UI設計.md#表示モードと状態遷移) 参照）、視点移動が発動しすぎて操作の邪魔になったため、発動条件を明文化して制限する。

関連: [全体設計.md](全体設計.md) / [UI設計.md](UI設計.md) / [実装計画.md](実装計画.md)

---

## 基本原則

1. **キャンバス内での直接操作では視点を動かさない。**
   ユーザーはすでにその場所を見ている。クリック/ダブルクリックした対象が画面内にあるのに視点が動くのは邪魔でしかない。濃淡（薄表示）の変化だけで応える。
2. **「探して飛びたい」意図の操作だけ視点を動かす。**
   左パネルの一覧クリックや検索は「画面外にあるかもしれないものを探す」操作なので、対象へ視点を移動する。
3. **明示的なボタン操作（フィット/再レイアウト等）は常に動かす。**
   ユーザーが自分で押したのだから期待通りに動かす。
4. **自動処理（手動リロード後の再パース・編集適用後の再パース）では視点を維持する。**
   作業中に勝手に視点が飛ばない。（2026-07-14: ファイル監視は廃止し手動リロードに変更したが、
   「処理後は視点を動かさない」という原則自体は不変。[計画-保存UNDO計画.md](計画-保存UNDO計画.md)）

> 実装原則: 視点移動は viewMode の変化から**導出しない**。「視点を動かすべき操作」だけが明示的にカメラコマンドを発行する（操作の出どころ＝キャンバス/パネル/検索/ボタン を区別する）。

## 発動パターン一覧（網羅）

### ファイル・自動処理

| # | イベント | 視点移動 | 内容 |
|---|---------|:-------:|------|
| F1 | ファイルを開く（初回ロード） | **する** | 全体フィット |
| F2 | 手動リロード（ユーザーがリロードボタンを押して再パース） | しない | 視点維持（作業の邪魔をしない）。※旧称「外部変更の自動リロード」。2026-07-14 にファイル監視を廃止し、発生源が「watchによる自動検知」から「ユーザーが手動リロードボタンを押す」に変わったが、視点を動かさない扱いは不変（[計画-保存UNDO計画.md](計画-保存UNDO計画.md)） |
| F3 | アプリ内編集の適用 → 再パース（保存前・保存後とも） | しない | 視点維持（編集した行を見続けられる）。編集はメモリ上の `currentText` 更新（Undo履歴に積む）であり、明示保存はこの視点維持には影響しない |

> **`modelUpdate` 種別の追加（2026-07-14）**: 明示保存 + Undo モデルへの移行に伴い、`modelUpdate` に
> **`'edit'`**（保存前の編集適用・Undo/Redo による再パース）が増えた。`'reload'`（F2 の手動リロード）と
> 同様に**視点は維持**する（F3 に整理済み）。詳細は [計画-保存UNDO計画.md](計画-保存UNDO計画.md)。

### キャンバス内の直接操作（原則: 動かさない）

| # | イベント | 視点移動 | 内容 |
|---|---------|:-------:|------|
| C1 | テーブルをクリック（フォーカス開始） | しない | 濃淡の変化のみ |
| C2 | フォーカス中に別テーブルをクリック（フォーカス移動） | しない | 薄いテーブルへの移動も含む |
| C3 | ダブルクリック（フォーカス + 行編集開始） | しない | その場で編集 |
| C4 | 背景クリック / Esc（フォーカス解除 → 全体モード） | しない | 濃淡が戻るだけ。視点はそのまま |
| C5 | ノードのドラッグ移動（フェーズ5） | しない | — |

### 左パネルの操作（原則: 対象へ動かす）

| # | イベント | 視点移動 | 内容 |
|---|---------|:-------:|------|
| P1 | テーブル一覧のクリック（フォーカス） | **する** | 起点 + 近傍にフィット（画面外の対象へ飛ぶための操作） |
| P2 | 表示範囲ボタンで数値変更（ホップ数） | **する** | 新しい近傍集合にフィット（範囲を見たい意図の操作） |
| P3 | 表示範囲ボタン「全体」 | **する** | 全体フィット |

### 検索（トップバー）

| # | イベント | 視点移動 | 内容 |
|---|---------|:-------:|------|
| S1 | 検索クエリ確定（ヒットあり） | しない | 濃淡の変化と左パネルの並び替えでヒットを把握する。飛びたいときは左パネルの一覧をクリック（P1） |
| S2 | 検索クエリ確定（ヒット 0 件） | しない | 「該当なし」表示のみ。視点はそのまま |
| S3 | 検索クリア（× / Esc / 空文字） | しない | 濃淡が戻るだけ。視点維持（見つけた場所に留まる) |

> 検索は一切視点を動かさない（2026-07-13 ユーザー決定）。「検索 → 左パネルでヒットを確認 → 一覧クリックで飛ぶ」という二段階の動線にする。

### 明示的なボタン・ショートカット

| # | イベント | 視点移動 | 内容 |
|---|---------|:-------:|------|
| B1 | ⊡（全体にフィット）/ `Cmd/Ctrl+0` | **する** | 全体フィット |
| B2 | ⟳（自動レイアウト再実行） | **する** | 配置が変わるので全体フィット |
| B3 | +/−（ズームイン/アウト） | **する** | ユーザー操作そのもの |

## 補足ルール

- **連続発動の抑制**: 視点移動はアニメーション（300〜400ms）付き。連続で発動した場合は最後の要求だけが有効（途中の移動は打ち切ってよい）。
- **フィットのパディング**: 対象群フィット時は 10% 程度の余白。1 テーブルだけへのフィットで過剰ズームインしない（最大ズーム率を制限）。
- **将来（フェーズ5）**: `.jpdbml.json` から配置を復元して開いたときも F1（全体フィット）と同じ扱い。

## パフォーマンス（パン/ズーム・描画）

視点移動そのものではないが、**パン/ズーム操作の体感速度**はこの設計と一体なのでここに記録する。大規模 DBML（手元の大規模サンプル、42 テーブル / 883 カラム）で「全体表示のパン/ズームが重い」問題を計測・改善した経緯と、残課題を残す。

### 計測でわかったこと（2026-07-14）

計測基盤を `src/perf/` に用意した（`perf.ts` の `perfSpan`/`markEvent`、`PerfOverlay.tsx`）。アプリ上で **`Cmd/Ctrl+Shift+P`** で計測オーバーレイ表示、**`Cmd/Ctrl+Shift+R`** で時系列トレースの記録開始/停止（停止時に scratchpad へ JSON を書き出す）。

- **パース（`@dbml/core` + 内部モデル変換）と ELK レイアウト計算はボトルネックではない。** Node 直実行で合計 63ms 程度。WebView 上でも初回一発。
- **遅さの主因は描画（DOM 量）。** テーブルノードの DOM は約 6,758 要素。パン/ズームは transform を毎フレーム更新するため、全要素が再合成され 1 フレームが伸びる。
  - 対策前: 全体表示のパン/ズーム中 平均 **28.2ms（35fps）** / カクつき（>33ms）率 **13%**。アイドル時は 57fps 出ており、常時負荷やリークではなく**操作中だけ**の問題。

### 実装済みの対策

| 対策 | 内容 | 効果 |
|------|------|------|
| `onlyRenderVisibleElements` | ビューポート外ノードを DOM から外す（React Flow 標準）。**全体俯瞰＝全テーブルが画面内のときは効かない**が、拡大時に効く。低リスク | 拡大時のみ |
| **LOD（詳細度切り替え）** | ズーム率 < `LOD_ZOOM_THRESHOLD`（現 **0.6**）のとき、テーブルノードはカラム行を一切描かず、**ヘッダー（青帯）＋本体エリアいっぱいの大きなテーブル名**だけにする（遠目で「どこに何の表があるか」を把握する用途。2026-07-14 ユーザー決定）。名前のフォントサイズは箱の幅・高さと表名長から自動フィット（`bodyFontSize`、12〜160px）。**外形サイズ（width/height）は通常時と同一に保つ**（座標・可視判定を崩さないため）。ズーム値は「閾値未満か」の bool として購読し、連続ズーム中は再レンダリングしない | 平均 35→50fps、カクつき 13→5% |
| **LOD 切替の遅延**（切替コストの退避） | 閾値をまたぐ瞬間に全ノードを一斉再構築すると 1 フレームに数千 DOM の生成/破棄が集中し **400〜470ms** の単発スパイクになる。これを**ズーム操作が完全に終わってから**（`onMoveStart`〜`onMoveEnd` の**終了**を起点に、`LOD_APPLY_DELAY_MS`=**120ms** 後）確定させ、操作の外へ逃がす。※「またいでから固定時間後」方式は小刻みズームの隙間で操作中に発火してしまい失敗した経緯あり | スパイクが操作中→操作の外へ移動 |

### 現状の到達点と残課題（次回チューニングの引き継ぎ）

- **到達点（2026-07-14 時点）**: 全体表示のパン/ズームは 平均 **48fps** / カクつき率 **7%**。常時のなめらかさは改善し、大スパイクは操作の外へ退避済み。ユーザー評価は「まあまあいい」。
- **残課題 1: LOD 切替 1 回が重い（約 450ms）。** 操作の外に出したので体感カクつきにはなりにくいが、「手を止めた直後→次に動かす境目」でまだ多少引っかかる。**全テーブルを 1 フレームで一斉再構築しているのが原因**。→ 切替をテーブル数個ずつ複数フレームに分割（`requestAnimationFrame` チャンク）すれば 1 フレームの重さを下げられる見込み。
- **残課題 2: B（行 DOM 削減）は未着手。** 通常（拡大）表示のカラム行は現在 1 行あたり約 5 要素（行 Box＋アイコン Box＋名前＋型＋note）。CSS 寄せで 2〜3 要素に減らせば拡大時・LOD 切替後の全カラム表示も底上げできる。全モードに効くがリグレッション確認が要る。
- **調整パラメータ**: `LOD_ZOOM_THRESHOLD`(0.6, `src/view/ErCanvas.tsx`) / `LOD_APPLY_DELAY_MS`(120, 同) / LOD 時の大きな表名フォントの自動フィット（`bodyFontSize`, `src/view/TableNode.tsx`、12〜160px にクランプ）。閾値を上げると LOD が効く帯が広がる（早め間引き）が、拡大途中で大きな表名のまま見える範囲も広がる。
- **計測手順の再現**: `Cmd/Ctrl+Shift+R` で記録 → 全体表示付近でズーム出し入れ → 再度 `Cmd/Ctrl+Shift+R`。出力 JSON の `summary`（平均 fps・カクつき率・最悪フレーム）と `timeline`（フレーム時間 + 操作イベント）で before/after を比較する。

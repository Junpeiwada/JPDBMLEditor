# spike: @dbml/core の位置情報調査

[実装計画.md](実装計画.md) フェーズ 1 の spike。フェーズ 4「最小編集で書式保持」の実装方式を左右する、`@dbml/core` のパース結果に含まれる位置情報（トークンレンジ）を実データで確認した。

調査スクリプト: [`src/parser/spike.mjs`](../src/parser/spike.mjs)（Node で直接実行可能。UI 起動不要）。

```
node src/parser/spike.mjs SampleDBML/<サンプル>.dbml
```

## 結論（要約）

**テーブル単位・カラム（フィールド）単位の両方でトークンレンジが取れる。** `Ref` の各エンドポイントにもトークンが付く。行番号ベースで元テキストを正確に切り出せることを実データで確認済み。フェーズ 4 の「最小編集で書式保持」は、このトークン情報をベースに実装できる見込み。

## 取れる情報の具体的なパス

`@dbml/core` の内部モデルは共通基底クラス `Element`（`node_modules/@dbml/core/types/model_structure/element.d.ts`）を継承しており、`Table` / `Field` / `Ref` はすべて `token: Token` を持つ。

```ts
interface Token {
  start: { offset: number; line: number; column: number };
  end:   { offset: number; line: number; column: number };
  filepath?: Filepath;
}
```

- **テーブル単位**: `table.token.start.line` 〜 `table.token.end.line`（`Table { ... }` ブロック全体）
- **カラム（フィールド）単位**: `field.token.start.line` 〜 `field.token.end.line`
- **テーブルの note**: `table.noteToken`（`note: '...'` 部分だけの範囲）
- **フィールドの note**: `field.noteToken`
- **Ref（リレーション）単位**: `ref.token`
- **Ref のエンドポイント単位**: `ref.endpoints[i].token`（`InlineRef` にも `token` あり）

line / column は 1 始まり、offset は 0 始まりの文字オフセット（両方とも実データで確認済み）。

## 実データでの確認結果

### 小規模サンプル（12 テーブル、Ref 0 件）

- 全 12 テーブル、フィールド合計 259 件をパース成功。
- 例（あるマスタテーブル。名前は架空のものに置換）:
  ```
  table.token: { start: { line: 26, ... }, end: { line: 46, ... } }
  field "所属部署CD" token: { start: { line: 27, ... }, end: { line: 28, ... } }
  ```
- テーブルのトークン範囲で元テキストを行スライスすると `Table <テーブル名> { ... }` ブロックがそのまま切り出せた。
- フィールドのトークン範囲で行スライスすると、そのカラム定義行 1 行（日本語カラム名・note 付き）がそのまま切り出せた。
- Ref が 0 件のスキーマでも `schema.refs` が空配列になるだけで、パース自体は問題なし（UI 設計の想定通り）。

### 大規模サンプル（42 テーブル、Ref 23 件、Enum・日本語 note 多数）

- 全 42 テーブル、フィールド合計 883 件、Ref 23 件をパース成功。
- 複合キーではない通常の Ref でも、各エンドポイントに個別の `token` が付与される（`M_XXX.取引先CD > M_YYY.取引先CD` のような Ref の両エンドポイントに同一行のトークン）。
- 日本語カラム名＋ `\n` を含む note（`note: '1：有効、2：無効\n自動採番で付与'` のような形式）でもトークン範囲・パース結果に問題なし。
- Enum 定義も同様にトークン付きで取得できる（`database.schemas[0].enums`、本 spike スクリプトでは未ダンプだが型定義上 `Enum` も `Element` 継承）。

## カラム単位で取れるか

**取れる。** `field.token` が各カラム定義の開始行〜終了行（次カラムの開始直前）を指す。フィールドのトークン範囲だけで元テキストの該当行をそのまま抜き出せることを両サンプルで確認した。

## コピペ・行並べ替えに耐える粒度か

- **単一カラムの追加・削除**: `field.token` の行範囲をそのまま使えば十分な精度。
- **複数カラムの並べ替え・コピペ（UI設計.md E-2 将来拡張）**: 各フィールドが独立した行範囲トークンを持つため、「カラム i のテキストを行範囲で切り出し、別の行位置に挿入し直す」という操作は原理上可能。ただし以下は自前で設計・実装する必要がある（`@dbml/core` はテキスト編集 API を提供しないため、あくまで読み取り用の位置情報）:
  - 複数行の同時移動時のオフセットずれ管理（1 箇所編集するたびに後続のトークンの line/offset がずれるので、編集は「末尾から」適用するか、都度再パースするかの方針が要る）。
  - フィールドのトークン範囲は「次フィールドの開始直前まで」を含む（小規模サンプルの例で `field.token.end.line === 次フィールドの開始 line`）。これは行末の改行を含む形になっており、行単位の削除・挿入とは相性が良い（1 フィールド = 1 行として扱える設計であれば、行の切り貼りだけで完結する）。
  - コメント行・独自ディレクティブ（`// @sequence ...` 等）は `@dbml/core` のトークンに含まれない（パーサが無視する）。これらの行は「どのフィールドのトークン範囲にも属さない行」として扱われるため、フィールド単位の行操作を行う際に**コメント行を巻き込まないよう、トークン範囲の外側にあるコメント行は触らない**設計にすれば書式保持できる見込み。実際にコメント行が絡む並べ替えの動作は、フェーズ 4 の実装時に個別サンプルで再検証が必要。
- 結論: **カラム単位の位置マッピングとしては実用に耐える粒度**。フェーズ 4 では「フィールド単位の行範囲」を編集の最小単位として扱う設計にする（末尾固定ではなく、任意のフィールドの前後に行を挿抜できる汎用的な実装にする）。

## 取れない場合の代替案（参考、今回は不要だった）

もし将来 `@dbml/core` のバージョンアップでトークン情報が失われる／取得できないケースに当たった場合の代替案:

- 自前の軽量トークナイザで `Table ... { ... }` ブロックと各行を正規表現ベースで再走査し、テーブル名・フィールド名から行番号を逆引きするマッピング層を `parser/` に追加する。
- パース前後でテキストを diff し、変更前後のテーブル定義ブロックをテキストブロック単位で置換する（トークン精度がカラム単位まで要らない場合の簡易策）。

今回はテーブル単位・カラム単位ともにトークンが取得できたため、これらの代替案の実装は不要と判断。

## 内部モデルへの反映

`src/parser/model.ts` の内部モデル型（`DbmlTable` / `DbmlColumn` / `DbmlRef`）に `token?: TokenRange` フィールドを追加し、`src/parser/parse.ts` の変換処理で `@dbml/core` の `table.token` / `field.token` / `ref.token` から実際に値を格納した（フェーズ 4 で使う想定。フェーズ 1 では読み取るだけで未使用）。

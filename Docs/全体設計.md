## 背景と目的

- DBML を書く/読むための専用デスクトップアプリ。
- 既存 VSCode 拡張の不満点:
  - ① ER 図プレビューの見た目・レイアウトが悪い → 描画エンジンを自前で握る
  - ③ VSCode の制約・動作が重い/使いづらい → VSCode の器から独立する
- VSCode はテキスト編集に使い続けてよい。本アプリは「見る・整える・軽く編集する」を快適にする。

## 技術スタック

- **器**: Tauri + Vite + TypeScript（Electron より軽量。前例: AnimeForgeStudio）
- **DBML パーサ**: `@dbml/core`（DBML 公式の TS パーサ）
- **ER 図描画**: React Flow + 自動レイアウト（dagre または ELK.js）
- **保存/取り込み**: 編集はメモリ上に保持し、明示保存（保存ボタン/Cmd+S）でのみファイルへ書き込む。ファイル監視（fs watch）は使わず、外部（VSCode 等）での変更は**手動リロードボタン**で取り込む（2026-07-14 決定。詳細は [計画-保存UNDO計画.md](計画-保存UNDO計画.md)）
- **メタデータ**: `.dbml` の隣に `foo.jpdbml.json` を併置（配置座標などの見た目状態。DBML 本体は汚さない）

## VSCode との連携

- 連携方針: **疎結合**。VSCode は普通に `.dbml` を編集・保存するだけ。
- 本アプリはファイル監視をしない。VSCode 等での外部編集は、ユーザーが**手動リロードボタン**を押して
  明示的に取り込む（自動では反映しない。2026-07-14 決定、詳細は [計画-保存UNDO計画.md](計画-保存UNDO計画.md)）。
- **未保存編集がある状態でのリロード**は、上書きしてよいか確認ダイアログ（破棄確認）を出す。
- VSCode 拡張は MVP では不要。将来「右クリックで本アプリを起動」を足す余地あり。

## 主要機能（MVP）

### 1. 検索フィールドによる絞り込み

- 画面最上部に入力フィールドを常設。
- テキストを打つと、**テーブル名・カラム名**の両方を検索対象とし、一致したものを持つ**テーブル**を ER 図に表示（絞り込み）。
  - カラム名がヒットした場合も、そのカラムを含む**テーブル全体**を表示し、**該当カラムをハイライト**する。
- 入力が空なら全体 ER 図に戻る。

### 2. 全体 ER 図表示

- 検索が空のとき、全テーブルとリレーションを自動レイアウトで表示。

### 3. テーブルのフォーカス表示（近傍表示）

- 絞り込まれた（または任意の）テーブルをクリックすると、
  そのテーブルとリレーションでつながるテーブルだけを表示（近傍フォーカス）。
- **ホップ数を UI で可変**（スライダー等）。初期値は **1 ホップ**（直接つながるテーブルのみ）。
  値を上げると 2 ホップ・3 ホップ…と近傍を広げられる。

### 4. 編集機能

- フォーカス中のテーブルに対して編集ができる。
- MVP の編集操作: カラム（行）の追加。
- **反映方式**: 全体を逆生成せず、**変更箇所だけをテキストに最小編集**して書式（コメント・並び順・整形）を保持する。
  - MVP の実装現実解: カラム追加はテーブル定義ブロックの末尾に 1 行差し込む。
  - 「元テキストのどの位置がどのカラムか」の位置情報（レンジ）取得は `@dbml/core` の調査が必要（未決）。
- 編集は**即ファイルに反映しない**。メモリ上のテキストを更新するだけに留め、**明示保存（保存ボタン + Cmd/Ctrl+S）**
  でファイルに書き込む。あわせて**テーブル定義編集（カラム追加/編集/削除）の無限 Undo/Redo**
  （Cmd/Ctrl+Z・Cmd/Ctrl+Shift+Z）を持つ（テーブル位置・幅などの見た目状態＝サイドカーは Undo 対象外）。
  詳細設計は [計画-保存UNDO計画.md](計画-保存UNDO計画.md)。

## 画面レイアウト

```
┌─────────────────────────────────────────────┐
│ [ 検索フィールド                          ]  │  ← 最上部・常設
├─────────────────────────────────────────────┤
│                                             │
│            ER 図キャンバス                   │
│      （全体 / 絞り込み / フォーカス）          │
│                                             │
└─────────────────────────────────────────────┘
```

## データフロー

```
.dbml ファイル
  → 開く/手動リロードで読み込み
  → @dbml/core でパース（テーブル/カラム/リレーション構造化）
  → 検索/フォーカス状態でフィルタ
  → 自動レイアウト（dagre/ELK）
  → React Flow で描画
  → （編集時）構造 → DBML テキスト生成（メモリ上の currentText を更新、Undo履歴に積む）
  → 明示保存
```

## 決定事項（相談で確定済み）

- 器は Tauri + Vite + TypeScript。
- VSCode とは疎結合（ファイル監視はせず、外部変更は**手動リロードボタン**で取り込む。2026-07-14 決定）。
- 検索はテーブル名・カラム名の両対象。カラムヒット時もテーブル全体を表示し該当カラムをハイライト。
- フォーカスのホップ数は UI 可変（初期値 1）。
- 編集の反映は「変更箇所の最小編集」で書式保持。MVP はカラム追加から。
- 編集は**明示保存**（保存ボタン/Cmd+S）でのみファイルに書き込み、**無限 Undo/Redo** を持つ
  （2026-07-14 決定。[計画-保存UNDO計画.md](計画-保存UNDO計画.md)）。

## 未決事項・調査ポイント

- **`@dbml/core` の位置情報**: パース結果から「元テキスト上のカラム/テーブルのレンジ」を取れるか。
  取れない場合、最小編集をどう実装するか（自前で軽量な位置マッピングを持つ等）。
- **自動レイアウト**: dagre と ELK.js のどちらが ER 図に向くか（ELK の方が高品質だが重い傾向）。
- **カラム追加 UI**: 型・制約（PK/NOT NULL 等）の入力をどこまで MVP に入れるか。
- **リレーション表示**: DBML の `Ref` をエッジとしてどう描くか（1:1 / 1:N の表記）。
- **将来拡張**: テーブル追加/削除、リレーション編集、テーマ、右クリックでの本アプリ起動（VSCode 連携強化）。

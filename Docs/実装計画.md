## 方針

- **層積み**: 各フェーズ完了時に単体で動作確認できる。手戻りを最小化する。
- **リスク前倒し**: 最大のリスク「最小編集で書式保持」に関わる `@dbml/core` の素性を、フェーズ 1 の中で小さく確認しておく（本格実装はフェーズ 4）。
- **コミット**: 各フェーズ完了時にコミット（ユーザー指示があったときのみ実施）。
- **進捗管理**: 本ドキュメントの各タスクはチェックボックスで管理する。実装・確認が済んだら `[x]` を付ける。
- **UI コンポーネント**: MUI を使用する（2026-07-13 確定）。トーストは notistack を併用。

## ファイル構成とメタデータ

- スキーマ本体: `foo.dbml`（DBML。純粋なまま保つ）
- アプリ用メタデータ: `foo.jpdbml.json`（`.dbml` の隣に併置）
  - 保存内容の想定: テーブル配置座標、フォーカス状態、ホップ数、色分け、折りたたみ状態など「見た目の状態」。
  - `.dbml` を移動・共有するときは `.jpdbml.json` も一緒に運べる。
  - メタが無い/壊れている場合は自動レイアウトにフォールバック（メタは常に「あれば使う」補助情報）。

## フェーズ 5: メタデータ永続化（配置保存）

- [x] テーブルをドラッグして配置を変更できる（2026-07-14 実装済み: テーブル名の青いヘッダー＝タイトルバーを掴んだときだけ移動。`dragHandle: '.table-drag-handle'`。ヘッダー以外を掴んだドラッグはキャンバスのパンに回す）。
  - 当初 `<ReactFlow>` に `onNodesChange` を渡しておらず、掴んでもノードが動かなかった（制御モードで変更の受け手が無かった）。`ErCanvas` に `handleNodesChange` を追加し、`applyNodeChanges` で `position`（ドラッグ移動）を `layoutNodes` に反映して修正（2026-07-14）。
- [x] 配置座標を `foo.jpdbml.json` に保存し、次回読み込み時に復元（2026-07-14 実装済み）。
  - サイドカー読み書きは `src/meta/sidecar.ts`（`.dbml`→`.jpdbml.json` パス導出・`readSidecar`/`writeSidecar`。`.dbml` 本体は一切書き換えない）。`{ version, tablePositions: { <tableId>: {x,y} } }` 形式。ユーザーが動かしたテーブルのみ載せる。
  - `useDbmlFile` がファイルオープン時にサイドカーを読み `savedPositions` を公開、`saveTablePositions` で書き込む。`App` がドラッグ完了通知（`onPositionsChange`）を 500ms debounce してサイドカー保存（アンマウント時は取りこぼし防止で即保存）。
  - レイアウト確定時、`ErCanvas` は保存済み座標（`savedPositionsRef`）を ELK 結果より優先して採用。座標変化で ELK 再計算は走らせない。
  - Tauri 権限 `fs:allow-exists` を `src-tauri/capabilities/default.json` に追加（サイドカー存在確認用）。
- [x] メタが無ければ自動レイアウトにフォールバック（`readSidecar` が無い/壊れ/スキーマ不正なら null を返し、`savedPositions` が空 → ELK 座標を使用）。
- [x] **完了条件**: 配置を動かして再起動しても位置が復元される（2026-07-14 ユーザー確認済み）。
- [x] （追加対応）ドラッグ移動中のパフォーマンス改善（2026-07-14）。
  - チラつき（全ノード再描画）: ノードの `data`（ハイライト・濃淡・コールバック）生成を座標から分離し、`nodeDataById`（テーブルID→data マップ）を座標に依存しない依存配列で `useMemo` 化。座標だけ動くフレームでは `data` 参照が保たれ、`TableNode`(memo) は動かした1個以外を再レンダリングしない。
  - 白フラッシュ（一瞬ノードが消えて再描画）: `handleNodesChange` で `position` だけでなく `dimensions`（measured サイズ確定）change も `layoutNodes` に反映。捨てると再生成時に measured が失われ `onlyRenderVisibleElements` の可視判定がリセットされて全ノードが一瞬消えていた。

## フェーズ 6: 明示保存 + Undo（ファイル監視廃止）

**2026-07-14 決定**: 「編集＝即ファイル上書き」「ファイル監視で外部変更を自動再描画」というフェーズ1〜4のモデルを、
「編集はメモリに溜め、明示保存で書き込む」モデルへ作り替えるフェーズ。あわせてテーブル定義編集の無限 Undo/Redo を導入する。
設計の詳細・決定事項・実装タスクは本ドキュメントではなく [計画-保存UNDO計画.md](計画-保存UNDO計画.md) に集約する。

- [ ] `useDbmlFile` に `currentText` / `savedText` / `isDirty` と編集適用・Undo/Redo・保存 API を実装。
- [ ] `watch`（ファイル監視）と外部変更検知・保存衝突ダイアログを撤去。
- [ ] インライン編集（挿入/更新/削除）のコミットを「readTextFile → 即write」から「currentText への最小編集 → applyEdit」へ移行。
- [ ] Undo/Redo スタックとショートカット（Cmd/Ctrl+Z・Cmd/Ctrl+Shift+Z、入力要素フォーカス時のガード込み）。
- [ ] 保存ボタン + Cmd/Ctrl+S、dirty インジケータ。
- [ ] 手動リロードボタン（未保存時は破棄確認 → 取り込み後は Undo 履歴クリア）。
- [ ] 未保存破棄ガード（ファイル切替・ウィンドウクローズ）。
- [ ] SampleDBML で一連の編集→Undo→Redo→保存→再オープン→手動リロードの手動確認。
- [ ] **完了条件**: 保存ボタン/Cmd+Sで明示保存するまでファイルが変更されない。Undo/Redoが効く。外部編集は手動リロードでのみ取り込まれる。未保存のまま別ファイルを開く/閉じると破棄確認が出る。

## 技術検証（spike）で先に潰す点

- **`@dbml/core` の位置情報**: パース結果から元テキスト上のテーブル/**カラム単位**のレンジが取れるか（フェーズ 1 で確認）。単なる末尾追加だけでなく、将来のコピペ・並べ替え（複数行を任意位置に挿入/移動）に耐える粒度かまで見極める。取れない場合は自前の軽量位置マッピングの実装コストを見積もる。
- **インライン編集の実装基盤**: React Flow のノード内で Excel ライクなセル編集（`Tab` 移動・複数行選択・行ドラッグ並べ替え）をどう実装するか。ノード内で独自グリッドを組むか、グリッドライブラリを埋め込むか。ノード移動と行内ドラッグの掴み分けは決定済み（2026-07-14: ノード移動はヘッダー限定 `dragHandle`、ヘッダー以外はパン。行並べ替えハンドルは行左端に置いて分離）。[UI設計.md の D](UI設計.md#d-テーブルノード)を参照。
- **自動レイアウト**: dagre と ELK.js のどちらが ER 図に向くか（フェーズ 1 で両方軽く試して選定）。→ **ELK.js に確定**（2026-07-13 ユーザーが実データで比較して選定。dagre は依存ごと削除）。
- **ファイル監視の粒度**: ~~Tauri の fs watch でエディタ保存（一時ファイル経由の保存も含む）を確実に拾えるか。~~
  → **2026-07-14 方針転換によりこの論点は解消**: ファイル監視自体をフェーズ6で廃止し、外部変更は手動リロードボタンで
  取り込む方式にしたため、watch の検知粒度を検証する必要がなくなった（[計画-保存UNDO計画.md](計画-保存UNDO計画.md)）。

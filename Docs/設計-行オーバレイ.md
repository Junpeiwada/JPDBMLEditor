# 設計: 行オーバレイ（カラム行に重ねる操作UI）の最終形

テーブルノードのカラム行には、表示テキスト以外に**行に重ねて出す操作UI**（並べ替え ▲▼、列リサイズハンドル、インライン編集行）が積み重なってきた。個別に追加してきた結果、オーバレイ同士・オーバレイとセル操作の衝突が起きている（後述の調査で、**実データでは全テーブルの note セル右端が ▲▼ に覆われ、ダブルクリック編集が奪われる**ことを確認）。本書はオーバレイ全体の最終形（原則と配置）を定め、個別修正のもぐら叩きを止める。

関連: [UI設計.md](UI設計.md) / [全体設計.md](全体設計.md) / [計画-幅調整.md](計画-幅調整.md) / [設計-視点移動.md](設計-視点移動.md)

---

## 現状のオーバレイ一覧

カラム行（4列グリッド: アイコン | 名前 | 型 | note）の上に重なる要素。種類で性質が違う。

| # | オーバレイ | 種類 | 表示条件 | 位置 | クリックを奪うか |
|---|-----------|------|---------|------|:---:|
| O1 | 並べ替え ▲▼ | 浮遊（行に重ねる） | フォーカス起点 + 行ホバー | 行の右端に絶対配置（right:8px、実測幅36px） | **奪う**（click/dblclick/contextmenu を stopPropagation） |
| O2 | 列リサイズハンドル | 浮遊（列境界に重ねる） | ノードホバー | 各列境界に幅7pxの縦帯（zIndex:2）、本体エリア全高 | **奪う**（mousedown=ドラッグ開始、dblclick=オートフィット。これは意図した専用領域） |
| O3 | インライン編集行（ColumnEditRow） | **置換**（表示行と入れ替え） | 編集/追加中の1行のみ | 表示行と同じグリッド位置（2026-07-14 決定: 1段目=同グリッド、PK/NN/default は直下の補助段） | 行全体が入力UIなので該当なし |
| O4 | FK/PK 接続ハンドル | 不可視 | 常時 | 行の左右端 | 奪わない（pointerEvents: none） |

「ホバー中のみ表示」は描画負荷対策（大量テーブルでの常時描画回避）として妥当で、最終形でも維持する。問題は**表示条件ではなく配置**にある。

## 調査結果（2026-07-14 実測）

### 1. ▲▼ は実データの全テーブルで最右列を覆っている

ノード幅は `estimateTableNodeSize` が「列幅合計 + 8px」で決めるため、**右余白は原則 8px しかない**（ヘッダー（表名）が列合計より広いテーブルだけ余白が増えるが、サンプル実データでは 0 件）。▲▼ は右端から実測 44px（right:8 + 幅36）を占めるので、**最右列（通常 note 列）の右側 36px が常に覆われる**。

パーサ + 概算関数での定量調査（列最小幅導入後の作業ツリーで実施。右余白 8px は最小幅と無関係に main でも同じ）:

| データ | ▲▼ が最右列に重なるテーブル |
|--------|:---:|
| 大規模サンプル（42テーブル） | **42/42**（全て右余白8px → 36px 被覆） |
| 小規模サンプル（12テーブル） | **12/12**（同上） |

[TableNode.tsx](../src/view/TableNode.tsx) 冒頭の既知事項「▲▼ は note 列の1行目に重なることがある（読めるので許容）」は**表示の話としてのみ**評価しており、下記の操作剥奪は未考慮だった。「狭いときに重なることがある」ではなく「常に重なっている」が実態。

### 2. ダブルクリック編集が ▲▼ に奪われる（操作の剥奪）

`elementFromPoint` での実測: フォーカス済みテーブルの note セル中央にある要素は note テキストではなく**「カラムを上へ移動」ボタン**だった。e2e（note-edit.spec.ts）でも、note セルのダブルクリックが編集にならず**カラムが移動してしまう**ことを確認。

未フォーカスのテーブルでも起きる。イベント連鎖:

1. note セルをダブルクリック（1打目のクリック）
2. 1打目でテーブルがフォーカス起点になり、▲▼ が**マウス直下に出現**する
3. 2打目が note セルではなく ▲ に当たり、編集開始の代わりにカラム移動が発火

補足: ▲▼ は非ホバー時 `opacity: 0` だが、**opacity はヒットテストに影響しない**ため、見えていなくてもクリックは奪う（フォーカス起点であれば常に）。

### 3. オーバレイ同士の衝突（▲▼ × リサイズハンドル）

note 列右端のリサイズハンドル（幅7px・zIndex:2）は ▼ ボタンの上に重なる（mini テーブル実測: ハンドル帯 232.5〜239.5px、ボタン領域 204〜240px）。この帯の中では ▼ を押したつもりが**列リサイズのドラッグが始まる**。

### 4. 編集行オープン中もリサイズハンドルが残る

O2 のハンドル帯は本体エリア全高に敷かれるため、編集行（O3）を開いている間も**入力欄の上に 7px の帯が残り**、そこを押すと編集中に列リサイズが始まる。実害は小さいが、最終形では「編集中はハンドルを出さない」で消せる。

### 5. 顕在化の経緯（この設計書を書くきっかけ）

編集行を表示行と同グリッド化した際、短いカラム名でも入力欄が潰れないよう列に最小幅（名前80 / 型56 / note56px）を導入した。これで小さなテストテーブルでも右余白が 8px になり、上記 2. が e2e で顕在化した。ただし前述のとおり**実データでは導入前から全テーブルで起きていた**問題であり、最小幅の撤回では解決しない。

## 問題点の整理

- **P1（最重要）**: ▲▼ が note セルを覆い、note のダブルクリック編集（E-2 セル直接編集）を奪う。実データで全テーブル該当。
- **P2**: フォーカス遷移のクリックで出現した UI が、同じ位置への次のクリック（ダブルクリックの2打目）を奪う。
- **P3**: ▲▼ とリサイズハンドルの領域が重なり、▼ を押したつもりが列リサイズになる帯がある。
- **P4**: 編集行を開いている間もリサイズハンドル帯が入力欄の上に残る。
- **P5（既知・許容済みだが関連）**: カーソル固定で ▼ を連打すると1行分を往復する（行のDOM移動にボタンが追従するため。キーボードの Enter 連打では起きない）。

## 最終形の設計原則

1. **浮遊オーバレイはセルの上に置かない。** クリック/ダブルクリック/右クリックはセルの操作（選択・編集・メニュー）のためにある。浮遊オーバレイは**専用の予約領域**（ガター・列境界の帯）にのみ置く。「重なっても読める」は許容できても「操作を奪う」は許容しない。
2. **出現直後のクリックを奪わない。** クリックで出現する UI は、その出現クリックと同じ座標を占有しない位置に置く（P2 はこれで構造的に消える）。
3. **オーバレイの予約領域同士も重ねない。** ガターと列境界ハンドルの座標は単一の定数群（nodeSize.ts）から導出し、交差しないことを計算で保証する。
4. **置換オーバレイ（編集行）は表示行と同じ座標系。** 1段目は表示行と同グリッド・同行高・同じ字面位置（枠は幅を消費しない inset shadow で描く）。表示行に対応する列が無い属性（PK/NN/default）は直下の補助段にせり出す（2026-07-14 決定・実装済み）。
5. **編集中は浮遊オーバレイを消す。** 編集行が開いている間、そのテーブルの ▲▼・リサイズハンドルは表示しない（P4 対応。編集は一度に1行なので操作は競合しない）。
6. **ホバー時のみ表示は維持する**（描画負荷対策）。ただし表示/非表示は見た目（opacity）だけでなく**ヒットテストも一致させる**（非表示中は pointer-events も切る）。
7. **編集中のテキストは絶対に切らない（2026-07-14 ユーザー決定・最優先）。** 入力内容が列幅を超えたら、**その列を（表示行も含めて）ライブで広げ、テーブルの箱も追従させる**。全行共通のグリッドテンプレートごと広げるため、原則4（表示行との列位置一致）は保たれたまま伸びる。確定/破棄で元に戻る（確定時は新しい内容の自動幅が引き継ぐ）。位置一致と切れないことが両立できない場面では**切れないことを優先**する。

## 選択肢（P1〜P3 の解法 = ▲▼ の置き場）

### 案1: 行の右端に ▲▼ 専用ガターを常時確保する（推奨）

ノード幅の概算（nodeSize.ts）に右ガター（≒44px、▲▼の実測幅+余白）を常設し、▲▼ はガター内にのみ描く。note 列はガターの左で終わるため重ならない。

- 長所: P1/P2/P3 が全て構造的に消える（ガターはセルでも境界でもない予約領域）。**モードが変わっても箱のサイズ・座標が一切動かない**（「配置は動かさず濃淡だけでモードを表現する」という既決の原則と整合）。リサイズハンドル（note 右端）はガター左境界に置けて衝突しない。
- 短所: 全テーブルが常時 ≒44px 広くなる。非フォーカス時のガターは空白（図の密度がわずかに下がる。note 列上限 180px と比べれば小さい）。
- 実装: nodeSize.ts に `MOVE_GUTTER` 定数を追加し `estimateTableNodeSize` / リサイズハンドル座標 / ▲▼ の right 値が同じ定数を参照する。

### 案2: ガターはフォーカス起点テーブルのみ ★採用（2026-07-14 ユーザー決定）

案1 と同じガターを、フォーカス起点（reorderable）のときだけ確保する。

- 長所: 全体モードの見た目が現状から一切変わらない。
- 短所: フォーカスのたびに箱幅が +44px 跳ね、右辺から出るエッジの端点も動く（原則「配置を動かさない」の例外になる。この点をユーザーが了承の上で採用）。
- 実装方針: ガターは**レイアウト状態（layoutNodes の style.width）には入れない**。フォーカス状態を知っている最終ノード派生（ErCanvas の nodes useMemo）で、フォーカス起点の style.width にのみ `MOVE_GUTTER_WIDTH` を加算する派生値として扱う。押し出し判定・サイドカー保存はガターを含まない基準幅のまま（ガターは一時的な view 装飾であり永続情報ではない）。TableNode 側は列ドラッグ中の previewWidth に同じ定数を加算する。

### 案3: ▲▼ を左端（アイコン列）に縦積みで置く

▲ を行の上半分、▼ を下半分に置く（幅 ≒18px、アイコン列を少し広げる）。

- 長所: ノード幅が広がらない。note のダブルクリックは奪わなくなる。
- 短所: アイコン列のダブルクリック（= name 編集開始にフォールバックする領域）を奪う（P2 が左端で再発）。PK/FK アイコンとホバーのたびに入れ替わりチラつく。ボタンが小さく押しにくい。

### 案4: ホバーボタンを廃止し、右クリックメニュー + キーボードに退避

行の右クリックメニュー（既存: 上に追加/下に追加/削除）に「上へ移動/下へ移動」を追加し、選択行に `Alt(Option)+↑/↓` を割り当てる。

- 長所: 浮遊オーバレイ自体が消えるので P1〜P3 と **P5（往復クリック）も全部消える**（キーボード連打は行に追従して連続移動できることが実証済み）。図が最も綺麗。
- 短所: マウスだけの連続移動はテンポが落ちる（1移動ごとに右クリック→選択）。「ホバーで ▲▼」という 2026-07-14 のユーザー決定を覆す。
- 補足: 案1 と排他ではない（案1 にキーボード/メニューを**追加**するのは常に可能で、P5 の緩和になる）。

### 案5: 現状維持（列最小幅だけ撤回する）

- 不成立に近い。実データでは最小幅と無関係に全テーブルで P1 が起きており、問題を「小さなテーブルでは見えない」状態に戻すだけ。

|---|:---:|:---:|:---:|:---:|---|---|
| 案1 ガター常時 | ○ | ○ | ○ | ×（残る） | 全テーブル +44px | ○（配置不変の原則に合致） |

## 実装ノート（原則4=編集行で得た知見。他のオーバレイ実装でも使う）

- 入力枠の枠線は `border` でなく **inset `box-shadow`** で描く。border/padding は内容幅を内側から削り、表示では収まる字面が編集中だけ見切れる/折り返す。
- `datalist` 付き input は Chromium が内部にピッカー矢印（≒14px）を描き字面を押し出す。`&::-webkit-calendar-picker-indicator { display: none !important }` で消す（`!important` 必須）。
- 複数行 note の入力欄は表示側と同じく**自動折り返し禁止**（`whiteSpace: 'pre'`）。折り返すと編集中だけ行数が増えて行高がズレる。
- note の1行目には表示側と同じ上余白 `(ROW_HEIGHT - NOTE_LINE_HEIGHT) / 2` を与えて字面の縦位置を一致させる。
- 位置一致の e2e は `e2e/edit-row-align.spec.ts`（列位置・列幅・字面の中心・note 1行目の縦位置を許容誤差 1.5px で実測）。
- 自動列幅は canvas measureText の実測ベース（2026-07-14 移行）。文字数×固定係数の概算は大文字英字で実描画より狭く出て、表示の「…」と編集欄の見切れを生んでいた（実測: `HKDメンテナンス数` 概算119px vs 実描画128.5px）。詳細は [計画-幅調整.md](計画-幅調整.md) の追記。
- 長い note（列上限 `NOTE_MAX_WIDTH`=180px で省略）の編集欄は、編集中だけ行の右端側（行パディング + ▲▼ガター = 52px）へ延長する（Excel の「編集中セルが隣にはみ出す」感覚。原則5で編集中の浮遊オーバレイは消えているため下敷きは無い）。
- 原則7（ライブ拡張）の実装: ColumnEditRow が入力のたびに必要列幅（`editContentColumnWidth` = canvas 実測 + 余白）を通知し、TableNode が列ドラッグプレビュー（`resizingCols`）と同じ仕組み（`editCols` → グリッドテンプレート + `previewWidth`）で列と箱をローカルに広げる。ErCanvas の `style.width`・押し出し判定・サイドカーは触らない（一時的な view 状態）。note は +52px 延長で足りない分だけ列を広げる。e2e: `edit-row-align.spec.ts`「編集中に長い文字を打つと列ごとライブで広がり、テキストが切れない」。
